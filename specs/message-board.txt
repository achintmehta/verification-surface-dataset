## Context

We are building a traditional client-server web application with real-time capabilities. To minimize external dependencies while retaining the power of PostgreSQL, we are using PGLite embedded within a Node.js server. Real-time updates will be pushed to the client using Server-Sent Events (SSE).

## Goals / Non-Goals

**Goals:**
- Provide a simple message board where users can post text messages.
- Ensure all connected clients receive updates instantly when new messages are posted.
- Store data persistently on the local disk using PGLite.
- Keep the frontend incredibly simple and lightweight.

**Non-Goals:**
- User authentication and authorization.
- Rich text formatting or media attachments.
- Horizontal scaling across multiple server instances (PGLite is tied to the single Node instance).

## Decisions

**Decision 1: Embedded PGLite vs External Postgres**
- *Rationale*: PGLite allows us to run PostgreSQL directly inside the Node.js process. This means users don't need to install or configure a separate database service. It seamlessly handles raw SQL queries and can persist to the filesystem.

**Decision 2: Server-Sent Events (SSE) vs WebSockets**
- *Rationale*: We only need one-way real-time communication (Server pushing new messages to Clients). Clients can post new messages via standard HTTP POST requests. SSE is much simpler to implement, works natively over standard HTTP, and doesn't require a complex WebSocket library like Socket.io.

**Decision 3: Vanilla JS / Vite vs React**
- *Rationale*: Given the minimal UI requirements (a message list and a text input), Vanilla JS keeps the build extremely fast and the dependency tree small. Vite provides a great developer experience out of the box.

## Risks / Trade-offs

- [Risk] PGLite performance on very large datasets: Embedded WASM databases are incredibly fast but might struggle if the dataset grows to tens of gigabytes.
  - *Mitigation*: This is a local application and we expect message volume to be manageable for a single server instance.
- [Risk] SSE connection limits: Browsers have limits on the number of concurrent SSE connections per domain.
  - *Mitigation*: We only need one SSE connection per client tab, which is well within browser limits.

## Why

We need a fast, local-first collaborative message board that allows users to post messages and see updates in real-time. This provides an incredibly low-latency experience by keeping data local while ensuring all users see the same state instantly. It serves as an excellent demonstration of using embedded PGLite combined with Server-Sent Events (SSE) to create a robust, lightweight realtime application without external database dependencies.

## What Changes

- We are introducing a brand new traditional client-server web application.
- The backend will be a Node.js server using an embedded PGLite database for raw SQL queries, persisting data to the local disk.
- Real-time synchronization will be handled via Server-Sent Events (SSE).
- The frontend will be a simple, lightweight Single Page Application (Vanilla JS or React via Vite).

## Capabilities

### New Capabilities
- `realtime-board`: The core message board capability covering posting messages, viewing a message feed, and receiving live updates via SSE.

### Modified Capabilities
None (Greenfield project).
